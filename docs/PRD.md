# Crypto Trading Platform MVP — PRD v0.1
Scope: secure auth + 2FA, third-party sandbox KYC, paper wallet journal, limit/market spot trading, price-time matching, WebSocket data, admin RBAC, audit, fees and monitoring.
Stack: Java 21/Spring Boot, PostgreSQL, Redis, Next.js. One deterministic sequencer per market pair. Double-entry postings atomically coupled to reservations and settlement.
Milestone 1: architecture + executable paper-only domain prototype.
Milestone 2: auth, MFA, KYC sandbox and admin.
Milestone 3: PostgreSQL durable double-entry ledger and holds.
Milestone 4: engine, trading API and market data.
Milestone 5: security, load tests, E2E and deployment.
P0 gates: per-asset conservation, precision, duplicate request conflict, durable audit and reconciliation, crash-safe replay, no negative user balances, no access across roles, no live funds until independent compliance/security assessment.
Out of scope for MVP: real asset custody, on-chain withdrawals, live capital and regulated exchange launch.

## Round 011 — integer-safe synthetic order reservation
Website-first safety requirement: BUY quote collateral must be calculated as **ceil(priceCents × quantityMicroBTC ÷ 1,000,000)** USDC cents with exact BigInt arithmetic; SELL collateral is an exact integer count of 0.000001-BTC units. Price input has at most 2 decimals and quantity at most 6. Reject exponent/negative/overprecision values, overflows beyond bounded allowed price/quantity, and any order whose rounded-up hold exceeds currently available synthetic cents or micro-BTC. Canceled and canceled-all holds must release without duplicate mutation. Display the conservative reserve. The local demo has no executions, durable storage, or external APIs. Deployment acceptance additionally requires Vercel production branch=main, exact SHA, public HTTPS 200, desktop/mobile browser tests, and green CI.

## R017 — manually triggered, offline PAPER fill (P0 interactive demo)
The v0.9 candidate provides a user-visible **Simulate fill** action for an OPEN locally reserved order. This is a fabricated full settlement **at that order's limit price** with quote debit/credit rounded conservatively to whole cents; it is NOT automated price/time matching, a counterparty, live execution, durable journal or authentic platform trade. The synthetic simulation must update displayed available/locked USDC/BTC totals using exact integer unit calculations, transition history from OPEN to SIMULATED_FILLED, export `simulatedFills` separately from `executions:0`, and fail closed on negative/inconsistent holdings. Filling an already canceled/filled order or triggering a stale detached handler must never mutate synthetic funds twice. Reset/reload must erase the fabricated state. The UI must prominently disclose non-execution and keep `/api/paper-status` strictly NOT_READY/GET-only. Accept only after source CI, negative BDD, Chromium desktop/mobile and exact-main Vercel READY + HTTPS content provenance.

## R019 — fail-closed PostgreSQL PAPER balance conservation
Owner-scoped synthetic read-only balance responses MUST present precisely one BTC and one USDC row; parse PostgreSQL NUMERIC(38,18) as BigInt 18-decimal units (never JavaScript Number), require total = locked + available, never negative or overprecision. Missing/duplicate/inconsistent balance rows must return generic 503 without sensitive payload. Only allowlisted fields may be serialized. This is a guard on a disabled-by-default paper READ endpoint, not user login, token issuance, durable order placement, real funds, or confirmed production DB. Acceptance requires independent negative BDD, disposable real PostgreSQL integration, green GitHub CI, Vercel Production exact source SHA and public mobile/desktop browser validation.

## R020 — PostgreSQL transactional PAPER reservation primitive
Prior to enabling any public order API, isolated account-scoped PAPER holds MUST use a single PostgreSQL transaction per reserve or cancel, lock the owner+asset account row before computing active holds, and enforce nonnegative available = total − locked. Idempotency key reuse with identical owner/asset/amount must never reserve twice (including after release); mismatched replay or attempts to cancel a different account's hold must fail without mutation. Accept only positive non-exponential fixed-point USDC (≤2dp) and BTC (≤6dp), rejecting invalid IDs, treasury, overflow and overprecision before DB access. Negative and real concurrent PostgreSQL 16 BDD must exercise oversubscription, rollback, cancellation, separate accounts and the existing signed read-only API. This is **not** a public write route, browser persistence, matching/settlement, user authentication flow, or a real-money exchange. Release requires Site+Core CI, exact SHA Production READY and actual logged-out HTTPS/mobile/desktop verification.

## R021 — replay/cancel linearizability for disposable PAPER holds
A reservation idempotency retry must be linearizable with same-account cancellation. Both paths must serialize through the owner/asset `paper_ledger_accounts FOR UPDATE` row lock before deciding the externally observable hold state. A stale pre-lock ACTIVE snapshot cannot be returned after RELEASED commits; the same ID cannot be recreated or silently accepted with a different payload. Verify deterministic stale-read interleaving and two-connection PostgreSQL 16 lock contention in CI. This remains an **internal server-only primitive** with no public order write endpoint, user identity issuer, actual matching, persistent website UI, real assets or KYC.
